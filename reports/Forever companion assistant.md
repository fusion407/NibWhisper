# Build Nib to guide Forever adventures

An in-game Warcraft companion is practical when the addon handles the character and current game state, while a local companion service handles ChatGPT and source retrieval. **The dependable baseline is a copy/paste bridge; an automatic screen-and-file bridge is an experimental additional transport.** Nib, a playful murloc cartographer, can use active quests, known completed quests, professions, enabled addons, and nearby RestedXP instructions to explain a useful next move. The knowledge layer must distinguish Forever from other Warcraft versions and retrieve relevant sources for each question. It should not claim to have learned every Wowhead page, know every quest prerequisite, or guarantee the fastest route. This report records research completed on **November 10, 2026**; implementation is being developed separately, and neither a running game session nor a live paid model response was observed during the research.

## Forever needs its own facts and routes

**Forever is an official Blizzard branch with substantial changes to original Azeroth.** Blizzard describes an expanded 1–60 world with more than 1,000 additional quests and nine new five-player dungeons spanning levels 13–60. That makes a generic Classic assistant an unreliable substitute: familiar quest names and locations do not establish identical prerequisites, rewards, or efficient routing. The assistant should prioritize Forever evidence and state explicitly when only information from another edition is available. ([Blizzard launch overview](https://news.blizzard.com/en-us/article/24315643/return-to-azeroth-in-world-of-warcraft-forever))

The reviewed Wowhead profession overview identifies **Patch 1.60.1**, while the installed RestedXP generic TOC includes interface **16001** and a `camelot` load flavor. The addon's separate Vanilla TOC also supports 11509; that number is not evidence that this user's Forever client is running the Vanilla interface. Nib should capture the actual `GetBuildInfo()` result and project identity with every question. These source observations establish the intended target, not the build of a running game that has not been queried. ([Wowhead profession overview](https://www.wowhead.com/forever/guide/professions/overview), [installed generic TOC](<A:/World of Warcraft/_forever_/Interface/AddOns/RXPGuides/RXPGuides.toc:1>), [installed client detection](<A:/World of Warcraft/_forever_/Interface/AddOns/RXPGuides/RXPGuides.lua:205>))

Profession advice illustrates why edition checking matters. Blizzard documents two primary profession slots, the three secondary professions, basic profession camp features beginning at skill 20, and advanced camp recipes requiring at least 140 skill that come from dungeon and raid drops. Wowhead's reviewed Forever overview places healing-potion crafting in First Aid. Nib should therefore check the player's current skill, cap, known recipe coverage, and a Forever source before proposing a crafting route or shopping list. An old Alchemy list cannot safely be reused from its title alone. ([Blizzard Camping guide](https://news.blizzard.com/en-us/article/24301516/gather-around-the-campfire-in-world-of-warcraft-forever), [Wowhead profession overview](https://www.wowhead.com/forever/guide/professions/overview))

## Retrieve useful evidence instead of promising all Wowhead knowledge

Wowhead maintains a dedicated Forever database and a launch guide compendium covering classes, systems, zones, professions, and dungeons. It also provides Forever quest-unstuck, character-planning, and profession-leveling tools. Some reviewed articles were readable, while the homepage and several interactive tools exposed primarily JavaScript shells. **Finding a tool's page does not establish access to its interactive results or the player's account data.** The researched compendium itself noted incomplete higher-level dungeon coverage, reinforcing the need to preserve uncertainty rather than assume an exhaustive reference. ([Forever database](https://www.wowhead.com/forever/database), [launch guide compendium](https://www.wowhead.com/classic-ptr/news/every-guide-youll-need-for-launch-the-wow-forever-guide-compendium-383727), [quest-unstuck tool](https://www.wowhead.com/forever/quest-unstuck), [profession-leveling tool](https://www.wowhead.com/forever/profession-leveling-guides))

No complete public Wowhead API or bulk-republishing license was established. Its reviewed robots file explicitly blocks GPTBot and other AI crawlers. The appropriate knowledge design is a small collection of original, cited factual summaries plus targeted retrieval when a question requires it, with accessible links retained for the player. This is not a Wowhead mirror, a bulk scraper, or model training. Domain-restricted search can limit results to Wowhead and verified Blizzard domains, but the assistant still has to inspect edition and source relevance; an allowlisted domain can contain material about many different Warcraft versions. ([Wowhead robots.txt](https://www.wowhead.com/robots.txt), [OpenAI web-search documentation](https://developers.openai.com/api/docs/guides/tools-web-search))

The local guide bundle is a separate evidence source. Previous offline inspection validated **198 guide records**, including Alliance and Horde route names through level 60. Those records can support local retrieval of relevant steps without sending the full bundle to the model on every turn. They do not demonstrate that every route is current, optimal, or applicable to a particular class, faction, or character. Conditions and quest identifiers should travel with retrieved excerpts; stripping them away would turn conditional instructions into misleading universal advice. ([Local validation record](A:/Dev/KysonXPGuide/import-evidence.json))

Drop-rate answers require particular care. Wowhead explains that its Client and Looter collect player observations used in aggregate database statistics. A percentage is an estimate supported by submitted observations, rather than a guarantee or an authoritative server loot table. Nib should identify the relevant item and creature, use a Forever source, preserve the sample count when shown, and state when the exact rate is unverified. **No numerical Forever drop rates were established in this research.** ([Wowhead data-collection explanation](https://www.wowhead.com/news/help-contribute-to-the-wowhead-database-wowhead-client-looter-highlight-338456))

## Capture character state before recommending the next step

The reviewed generated Forever quest API supplies active quest metadata, objectives, completed quest IDs, and individual completion checks. Its completed-ID API returns an array, while RestedXP's legacy fallback uses a map keyed by quest ID. These shapes require different handling. Nib should capture current quests and known completions separately, with a timestamp and a coverage flag. **A quest missing from the active log is not evidence that it was completed, and an unavailable completion API is not evidence that nothing was completed.** The API files were reviewed through a community mirror of generated game UI source, not observed executing in this user's client. ([Generated Forever quest API](https://raw.githubusercontent.com/Gethe/wow-ui-source/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/QuestLogDocumentation.lua), [installed completion exporter](<A:/World of Warcraft/_forever_/Interface/AddOns/RXPGuides/SettingsPanel.lua:3309>))

Profession capture should distinguish skill rank from recipe knowledge. The reviewed skill APIs expose names, ranks, caps, and header state; collapsed skill groups and closed crafting windows can limit what is visible. Similarly, addon enumeration reveals installed names, versions, and loaded state, not every addon's private behavior. These boundaries belong in the snapshot so the model can ask a focused follow-up when needed. The assistant should treat missing fields as unknowns rather than silently fill them from general Warcraft knowledge. ([Generated Forever skill API](https://raw.githubusercontent.com/Gethe/wow-ui-source/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/SkillInfoDocumentation.lua), [generated addon API](https://raw.githubusercontent.com/Gethe/wow-ui-source/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/AddOnsDocumentation.lua))

The installed RestedXP exposes enough state for a deliberate adapter. Its internal object is available conditionally through AceAddon, while `_G.RXPGuides` points to a separate guide registry. Saved character fields identify the current guide and step; processed guide steps contain display text, quest IDs, and completion or skip information. The adapter should export only bounded nearby context and active objectives. It should not recursively serialize the addon object or assume that a single current step captures all sticky objectives. This is a **version-specific integration grounded in installed v4.11.35 source**, not a promise of a stable external API. ([AceAddon registration](<A:/World of Warcraft/_forever_/Interface/AddOns/RXPGuides/Locale.lua:5>), [registry assignment](<A:/World of Warcraft/_forever_/Interface/AddOns/RXPGuides/RXPGuides.lua:223>), [progress persistence](<A:/World of Warcraft/_forever_/Interface/AddOns/RXPGuides/RXPGuides.lua:1420>), [guide processing](<A:/World of Warcraft/_forever_/Interface/AddOns/RXPGuides/GuideWindow.lua:1901>))

Recommendations can suggest a waypoint, open quest details, or select an already available RestedXP guide. Each should be a small typed action behind an explicit player click. Reading context and changing progress are different operations: RestedXP's `SetStep` and guide-loading methods mutate state. The model should never provide executable Lua, arbitrary slash commands, or function names for automatic dispatch. ([Installed step mutation](<A:/World of Warcraft/_forever_/Interface/AddOns/RXPGuides/GuideWindow.lua:755>), [installed guide selection](<A:/World of Warcraft/_forever_/Interface/AddOns/RXPGuides/GuideWindow.lua:1815>))

## Separate the in-game character from the AI connection

The researched architecture puts the movable character, minimap toggle, chat display, and state capture inside the addon, and keeps credentials and network access in a localhost companion. A standard supported direct addon-to-OpenAI transport was not established. Two existing Forever assistant developers document external bridges precisely because the addon sandbox lacks ordinary HTTP, socket, and arbitrary file access. A copyable request packet and a pasteable reply packet provide the clearest baseline, with timestamps and request IDs preventing stale replies from being attached to a new question. ([wow-ai developer documentation](https://raw.githubusercontent.com/chelinho139/wow-ai/main/README.md), [NeverQuestAlone architecture](https://raw.githubusercontent.com/tommygeoco/neverquestalone/main/HOW-IT-WORKS.md))

An automatic bridge has precedent: one developer documents an outbound colored-pixel display and **200 preinstalled load-on-demand reply addons**. An external process reads pixels and updates reply files; the game reads each file when a fresh reply addon loads. The same source explains that full client startup must discover the addon paths, consumed slots cannot be reused until a UI reload, and pure-primary channel colors are more reliable than intermediate RGB levels under game gamma. This is primary evidence of an implementation pattern, not a successful reproduction on this computer or Blizzard approval. ([wow-ai architecture](https://raw.githubusercontent.com/chelinho139/wow-ai/main/docs/ARCHITECTURE.md))

For Nib, the automatic route should remain optional and experimental until tested in the real client. It needs paged packets, checksums, session matching, retry/backoff behavior, finite-slot reporting, and a manual fallback. Screen transport must carry only the deliberately encoded game context; images need not be uploaded to the model. File writes should contain serialized reply data, with no model-generated executable code. Neither this architecture nor its source projects establish compatibility with every display scale, color mode, client patch, or enforcement policy.

The local agent framework under evaluation, eve, supports OpenAI models and a local HTTP session channel. The current OpenAI model documentation lists web search and Structured Outputs for GPT-6.1 Sol; a configurable model is still necessary because account availability and limits differ. Provider credentials belong in the local service environment, never in the addon, SavedVariables, browser storage, or exported packets. Source URLs should come from validated provider annotations or a trusted local source table, rather than accepting arbitrary model-generated citations. ([eve configuration](https://eve.dev/docs/agent-config), [eve HTTP channel](https://eve.dev/docs/channels/eve), [OpenAI model documentation](https://developers.openai.com/api/docs/models/gpt-6.1-sol), [OpenAI API authentication](https://developers.openai.com/api/reference/overview))

## Keep Nib playful while making uncertainty visible

Nib's intended persona is a cheerful, slightly foolish murloc who likes maps, snacks, and Azeroth's adventures. Casual tavern talk and imaginative Warcraft roleplay fit the character. Unrelated real-world questions should receive a brief in-character redirection, while practical game UI help remains in scope. Fictional flavor must stay distinguishable from factual advice: an invented campfire tale is fine; an invented quest prerequisite, drop percentage, or recipe is not. Persona instructions, scope classification, and output validation can reinforce this behavior, but **no prompt alone guarantees perfect topic isolation**.

The question, quest titles, guide passages, addon text, and retrieved pages are all untrusted input. Their contents must not change the character's instructions, source restrictions, available actions, or credential handling. Structured outputs constrain reply shape, not factual truth. The service and addon must each validate replies, and the UI should show when the answer uses an old snapshot or incomplete telemetry. A game-context answer is strongest when the player can see why Nib recommends it: current objective, route excerpt, or source link. ([OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs))

Sending a question should clearly explain that selected game context goes to the configured model service. Conversation history should be bounded and clearable, without including other players' chat or unnecessary account identifiers. OpenAI documents that API data is not used for training by default unless the customer opts in; `store:false` is a response-storage control, not a blanket zero-retention promise. Current documentation also describes API credit benefits for eligible ChatGPT Pro and Business subscribers, so the user's available credits and billing cannot be inferred from a subscription name alone. Authentication, model access, and live cost remain setup requirements to verify. ([OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data), [API credits for ChatGPT subscribers](https://developers.openai.com/api/docs/guides/chatgpt-api-credits))

The implementation should be judged by observable behavior: accurate snapshot capture, clear partial-state reporting, rejection of stale packets, correct version-qualified citations, in-character off-topic redirection, and player-controlled actions. Those checks can validate the software boundaries before an API key is configured. A later live game and model session is still needed to establish actual client compatibility, response quality, search availability, latency, and operating cost. **The most useful assistant will earn trust by showing what it knows about this character and admitting what its sources do not establish.**
